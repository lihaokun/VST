### 对核心语义的进一步核对

1. **加强型定义不是语义重复错误。** `data_at && exact_representation` 同时要求 typed 合法性与表示约束。保留 ordinary conjunct 能避免把一般性的 `decode(encode(v)) = v` 当成无前提公理。代价是组合证明和 term 可能重复，属于已识别的工程成本，不构成否决理由。
2. **union 选择值与别名读取须分开。** 原 `reptype` 的和类型决定当前 exact 谓词描述哪个成员；读取其它重叠成员可以借出 typed 视图，不能因此把源值改成另一个成员，也不能并列持有两份重叠 SEP 资源。A 的 G3／I5 与 P 的 `&&` 借用形式符合这一点。
3. **拥有 padding 与知道 padding 内容不同。** `memory_block` 保有相应区域，并不指定其中是零、Undef 或某个确定数组。L:17–28 恰好验证了窄 union 的尾部与 struct 的中间空隙仍在。后续证明不能把它当成确定宽读的依据。
4. **精度只能由证据建立。** `data_at_`／`field_at_` 的未知值可以安全写入，不应先改成 exact PRE。P 的 ramification 对任意 `old` 表述，没有要求旧 exact；写后值则由真实赋值及 cast／tc 条件确定。A:160–164 的反例要求方向正确。

**无已坐实项。** 当前材料没有显示必须改变公开目标、替换底层逻辑或引入新公理才能完成首批接口的结构性矛盾。

## 4. 需决策／明确的公开合同

### D1：确认 exact 的对象是选定 typed 值表示，不是全对象逐字节已知

**位置：** A:45–66、124–129、174–175；R:54–67。

这是架构已经提出、明确等待确认的语义选择，不是审查发现的新缺陷，也不重开用户已确认的 typed API＋Agent 自动化目标。

应确认以下可观察结果：

- 全宽整数成员覆盖 union 整个存储范围时，可以建立全宽 exact；若仍有尾部空隙，则只保有该空隙，不声称其编码确定。
- 窄成员的 `exact_data_at` 可以表示完整 union ownership，但只固定该成员的编码，尾部仍未知。因此“完整 exact union”不承诺所有成员都有确定可读值。
- struct 的 exact 表示固定其有效值单元，padding 不固定；普通 struct 单字段写入不能把其它字段一并升级。
- 普通未知／未初始化空间继续使用普通 underscore 谓词；不能为方便自动化而新增一个冒充未知内容的 exact underscore。

**建议决策：接受 A／R 当前选择。** 它与 CompCert 表示事实、未知输入和局部 store 的信息量相符，且足够支持宽写后重叠读取。若用户实际要求包括 padding 在内的全字节精确性，则是不同的公开合同，不能在实现时悄悄替换本选择。

### D2：首批操作需按访问方向明确，尤其是窄成员写与高字／拆分读

**位置：** A:51、120–133；R:106–111。

R 将首批概括为非 volatile `tuint`／`tulong` 及相应 scalar 字段、union 成员；A 的具体矩阵明确承诺完整宽成员写，又把高字／拆分视图列入首批。两处不是已证明的逻辑矛盾，但“相应 union 成员”没有单独说明窄成员写及宽写后再窄写的承诺，容易在细化时出现范围分叉。

需固定的不是 tactic 语法，而是用户能依赖的操作集合：

1. 首批整数类型以 R 的 `tuint`／`tulong` 为准，不能把 A 的“非volatile整数场景”读成任意整数宽度和符号性均支持。
2. A 的高字／拆分视图若保留在首批，就是本批交付项，并须沿用各自实际偏移与端序条件；已有低字探针不能替代它们的 typed 桥接。
3. 窄 union 成员写是否属于本批？若属于，最小合同可采用“选定窄成员 exact＋其余空间仍保有”，但不得沿用已被覆盖的旧宽值；是否进一步保留未覆盖高字的已知精度，需要明确承诺。若不属于，应把该方向从笼统的“union 成员支持”中排除。

**建议决策：明确上述范围，窄写先采用现有选定成员语义，不附加保留全部历史字节精度的承诺。** 这不需要新 value record、通用重解释平台或第二套布局模型。超出该最低合同的精度保留只有在确属用户需求时再加入。

## 5. 建议与关键结构性风险

### S1：最高优先级——同一布局不自动给出两层资源的通用拆装定理

**位置：** A:35–49、96–102、137–140；R:103；P:14–34；L:9–41。

架构复用同一 aggregate 构造器是正确选择，但公开谓词是整个 ordinary aggregate 与整个 exact aggregate 的交。要得到逐字段的加强谓词，必须证明两套描述可以在同一资源切分上对齐。

一般 BI 逻辑中不能不加条件地使用：

```text
(P * F) && (E * G)  |--  (P && E) * (F && G)
```

两边各自存在一个分离见证，并不自动意味着见证相同。这里可能使对齐成立的依据是具体 typed 谓词的固定地址区域、share、共同布局和 spacer；这些必须成为结构引理的论证，而不是借助通用分配律跳过。

四个 layout case 只证明 `exact_representation` 的展开等式，尚未证明上述 ordinary／exact 对齐、通用 field focus、union 值分支更新或 reassembly。它们因此是好的可行性证据，但不是结构模块已经完成的证据。

**建议：** 将“资源切分对齐及其往返条件”置于结构层细化的首要证明义务，分别处理 array、struct、选定 union 分支和 padding。明确字段 focus 的结果及恢复父对象所需的资源；不能将另一个重叠 union 成员当成独立 frame。先解决这一层，再扩展自动化，可避免前端写完后才发现底层合同无法组合。

这是对必要引理合同及论证的要求，不要求架构阶段提供完整 tactic 证明。

### S2：高优先级——混合精度 POST 必须可被下一次 typed 操作继续消费

**位置：** A:60、99、106–118、128–129；R:60–64。

“普通 struct 单字段写后，得到该字段 exact＋原 typed frame”是正确方向，但前端必须知道 frame 指向未写的剩余区域。不能把 `exact_field_at` 与原完整 `data_at` 用 `*` 并列；后者本身已占有刚写字段，且其旧 typed 值可能已经失效。

如果第一次写后只得到客户端无法继续消费的残余 wand 或必须手工展开的布局，单次 store 规则即使 Qed，也不能满足 G4。反之，不能为维持一个整齐的单对象谓词，把原来其它字段的 exact 信息全部遗忘，再要求用户手工找回。

**建议在细化入口／出口合同中锁定三个连续场景：**

1. ordinary aggregate 单字段写后，资源保持完整，所写字段 exact，未写字段保持原普通事实。
2. 后续 typed load/store 能直接消费该混合状态；已有其它字段的 exact 信息在不被写覆盖时可沿用。
3. 所有选定有效值单元都具备所需 exact 事实时，可以由公开结构接口重组完整 exact aggregate，而不要求 padding 也已知。

具体采用字段级 SEP 还是库内部封装的残余形式可留在细化决定；当前无须发明混合精度 record 或全局精度跟踪系统。关键是模块输入输出可衔接，并符合 A 已承诺的局部升级及资源保持。

### S3：把自动化与泛化能力落实为后续验收，不用探针数量代替

**位置：** A:15–17、101–118、149–167；R:76–104。

现有验收方向合适：字段名／顺序变化、任意满足条件的 share、非零 SEP 位置、独立 frame、padding struct 都是高层接口需要跨越的真实差异。建议在此基础上重点覆盖 S2 的连续操作，以及 D2 最终确认的访问方向。

还需保留两项已经写入架构的责任：

- 常规路径可从 source fc／layout 推出的 target fc 应由库或前端解决。P:67–69 将 target fc 显式作为低字借用前提只是探针边界，不能直接变成每个客户端重复承担的后端任务。
- volatile 支持检查须覆盖有效路径／继承属性，不能只看叶子类型；失败也不能静默退回普通 forward 而丢掉精度。谓词可递归定义不提供 volatile 操作资格。

不建议增加通用注册平台、全类型解码器或新的证明判断。公开接口的正常客户端只使用 typed 层、所有证明最终由原 kernel 接受，已是本目标恰当的验收方向。
